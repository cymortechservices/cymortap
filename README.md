# CYMOR TAP — One tap. One conversation.

CYMOR TAP creates branded short links that open a WhatsApp chat with a message already typed in. Anyone can make a basic link without an account. People with an account can save, edit, turn off and delete links, download QR codes and see click analytics.

> **Status of this build.** The complete source code, tests and documentation are included, but this archive was generated in an environment with no network access. Dependencies were **not installed**, and the type check, lint, unit tests, API tests, end-to-end tests and production builds were **not run**. No lockfiles are included because they can only be generated by `npm install`. Run the commands in [Quick start](#6-local-installation) and [Tests](#12-how-to-run-tests) first and fix anything they report. See [Known limitations](#19-known-limitations).

## 1. What it is
A WhatsApp click-to-chat link generator. A link such as `https://tap.example.com/airforce-order` is resolved by the backend, which records an eligible click (for account links) and redirects the visitor to `https://wa.me/<number>?text=<encoded message>`. CYMOR TAP is independent and is not affiliated with WhatsApp or Meta.

## 2. Features
- Guest link creation, no account (default 90-day expiry, shown before generating).
- Optional accounts: register, login, logout, change password, password reset (honest about email delivery), account deletion.
- Country-aware phone validation (libphonenumber), international numbers incl. +254.
- Message editor: emojis, line breaks, WhatsApp formatting toolbar (*bold*, _italic_, ~strike~, monospace), counter, 11 template categories, live chat-style preview.
- Custom slugs with allowlist, reserved names, availability check and unique index.
- Redirect engine with disabled / expired / deleted / unknown handling, preview page (`?preview=1`) and optional HTML hand-off mode.
- Dashboard: overview, My Links (search, filter, sort, pagination, edit, enable/disable, delete), per-link and global analytics, CSV export, settings.
- Analytics: eligible clicks, estimated unique visitors, devices, referrers, date ranges, bot and preview filtering, de-duplication.
- QR codes (PNG, 1200px) pointing at the branded link; native share with clipboard fallback.
- Abuse controls: reports, auto-disable threshold, moderation CLI, rate limits.

## 3. Technology stack
Frontend: Next.js 15 (App Router), React 19, TypeScript strict, Tailwind CSS 3, Framer Motion, Lucide, Recharts, React Hook Form + Zod, qrcode, libphonenumber-js.
Backend: Node 20+/22, Express 4, TypeScript strict, Mongoose 8, Zod, Helmet, express-rate-limit, bcryptjs, nodemailer.
Data: MongoDB Atlas. Tests: Vitest, Supertest, mongodb-memory-server, Testing Library, Playwright.

## 5. Prerequisites
Node.js 20 or newer, npm 10+, a MongoDB instance (Atlas free tier or local), Git.

## 6. Local installation
```bash
git clone <your repo> && cd CYMOR-TAP
cd backend  && cp .env.example .env && npm install
cd ../frontend && cp .env.example .env.local && npm install
```
Commit the generated `package-lock.json` files so deployments use `npm ci`.

## 7. Frontend setup
`frontend/.env.local`:
```
NEXT_PUBLIC_API_BASE_URL=http://localhost:4000
NEXT_PUBLIC_SHORT_LINK_BASE_URL=http://localhost:4000
```
## 8. Backend setup
Edit `backend/.env` (see section 10). Locally the API itself serves branded links, so `SHORT_LINK_BASE_URL=http://localhost:4000` works with no DNS.

## 9. MongoDB Atlas setup
See [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md#mongodb-atlas). Then run `npm run db:init` in `backend/` once to create all indexes.

## 10. Environment variables
Frontend: `NEXT_PUBLIC_API_BASE_URL`, `NEXT_PUBLIC_SHORT_LINK_BASE_URL` (both public by design).
Backend: `NODE_ENV`, `PORT`, `MONGODB_URI`, `FRONTEND_URL`, `ALLOWED_ORIGINS`, `SHORT_LINK_BASE_URL`, `SESSION_SECRET` (≥32 chars, required in production), `SESSION_TTL_DAYS`, `COOKIE_SAMESITE`, `COOKIE_DOMAIN`, `GUEST_LINK_TTL_DAYS`, `REPORT_AUTO_DISABLE_THRESHOLD`, `REDIRECT_MODE`, `TRUST_PROXY`, `SMTP_HOST/PORT/USER/PASS`, `MAIL_FROM`, optional `LOG_LEVEL`. Every variable is documented in `backend/.env.example`. The server refuses to start in production without `MONGODB_URI` and a strong `SESSION_SECRET`.

## 14. Deploy the frontend to Vercel
Import the repo, set **Root Directory** to `frontend`, add the two `NEXT_PUBLIC_*` variables, deploy. Details in docs/DEPLOYMENT.md.
## 15. Deploy the backend to Render
Use `render.yaml` (Blueprint) or create a Web Service with root `backend`, build `npm ci && npm run build`, start `npm start`, health check `/health`. Set the environment variables, then run `npm run db:init` from a Render shell or locally against Atlas.
## 16. Configure the branded link domain
Point a subdomain such as `tap.yourdomain.com` at the Render service (custom domain + CNAME), then set `SHORT_LINK_BASE_URL=https://tap.yourdomain.com` on the backend and `NEXT_PUBLIC_SHORT_LINK_BASE_URL` on the frontend. The API serves `/<slug>` and `/r/<slug>`. If you prefer to keep the API on its default hostname, set `SHORT_LINK_BASE_URL=https://<service>.onrender.com/r`.

## 17. Troubleshooting
| Symptom | Likely cause |
|---|---|
| Browser console CORS error | `FRONTEND_URL` / `ALLOWED_ORIGINS` does not exactly match the frontend origin (no trailing slash) |
| Signed in but dashboard bounces to login | Cookies blocked cross-site. Use sibling subdomains of one domain with `COOKIE_SAMESITE=lax` and `COOKIE_DOMAIN=.yourdomain.com`; or `none` and accept third-party-cookie limits |
| 403 `CSRF_HEADER` | A client is calling the API without `X-Requested-With: cymor-tap` |
| Backend exits at start | Missing `MONGODB_URI` or short `SESSION_SECRET` in production |
| Atlas connection timeout | IP access list does not include Render's outbound addresses |
| Link opens but WhatsApp does not | Add `?preview=1` to see the destination; install WhatsApp or use WhatsApp Web |
| First Render request is slow | Free instances sleep when idle |

## 18. Security and privacy
Summary in [docs/SECURITY.md](docs/SECURITY.md): bcrypt password hashing (cost 12), HTTP-only server-side sessions, CSRF guard, CORS allowlist, Helmet, rate limits, Zod validation on every endpoint, ownership enforced in the database query, destinations built only from validated phone + message, no IP storage in click events.

## 19. Known limitations
- **Not yet installed, built or tested** (see top of this file).
- No lockfiles in the archive; generate them with `npm install`.
- A click is not proof that a WhatsApp message was sent. Unique visitors are estimates (the visitor code rotates daily).
- Guest links are not tracked and cannot be managed or claimed later (no secure ownership-transfer mechanism is implemented).
- Email address cannot be changed and is not verified; password reset needs SMTP.
- Cross-site cookies are limited by browsers; prefer sibling subdomains.
- Mongo TTL index on click events is fixed at 400 days; change in `EVENT_RETENTION_DAYS` and run `db:init`.
- Privacy Policy and Terms are sensible defaults, not legal advice.
- Dependency versions were chosen at generation time; run `npm outdated` / `npm audit`.
